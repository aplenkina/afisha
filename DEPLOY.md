# Релиз afisha-rb

Production-конфигурация находится в `compose.prod.yml`. PHP-образ содержит приложение, зависимости и собранные ресурсы; код с сервера в контейнер не монтируется. Порты PostgreSQL и Go наружу не публикуются.

## Подготовка

1. На сервере нужны Docker Engine и Compose. Направь DNS домена на сервер и открой входящие TCP 80 и 443 для Caddy. Для закрытой проверки ограничь доступ к стенду до публикации.
2. Из корня проекта создай файл настроек командой `(umask 077; cp -n .env.production.example .env.production)`. Укажи настоящий домен в `SITE_ADDRESS`, URL с HTTPS в `PUBLIC_URL`, независимые случайные значения для `APP_SECRET` и `DATABASE_PASSWORD`. Используй отдельные серверные значения. Файл не входит в образ и не должен попадать в архив релиза.
3. Присвой свежий уникальный тег каждому образу релиза: например, `export RELEASE_TAG=2026-11-19-01`. Во всех командах используй одинаковый тег. Для удобства объяви функцию:

```bash
prod() { docker compose --env-file .env.production -f compose.prod.yml "$@"; }
```

## Первый запуск

```bash
prod build
prod up -d --wait postgres
prod run --rm app php bin/console doctrine:migrations:migrate --no-interaction
prod exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < docker/postgres/bootstrap-prod.sql
prod run --rm app php bin/console app:user:create you@example.com admin
prod run --rm app-go ./main -once
prod up -d
```

Замени email администратора. Команда запросит пароль. Начальные записи создаются повторяемо: скрипт можно запустить снова, и он не перезапишет существующие города, категории и источники. Импортированные события сохраняются черновиками; опубликуй проверенные события в админке.

Проверь HTTPS, главную, страницу категории, вход в админку и путь от фильтра до карточки и ссылки на билет. Проверь `prod ps` и `prod logs --tail=100 app app-go`. Сборщик запускается ежедневно в 04:00 по Минску, если не указан `COLLECT_AT`. Telegram webhook можно подключить отдельным релизом; без `TELEGRAM_WEBHOOK_SECRET` он возвращает 403.

## Аналитика

После согласия на аналитические cookies публичные страницы загружают `GTM-WDZ888B5` и `GTM-KQTDN7CC`. Идентификаторы можно переопределить в `.env.production` через `GTM_CONTAINER_ID` и `GTM_EXTRA_CONTAINER_ID`. Пустое значение отключает соответствующий контейнер.

В Google Tag Manager настрой Google tag для веб-потока GA4 с обычным просмотром страницы. Для кликов по билетам настрой тег события GA4 `ticket_click` с одноимённым триггером «Пользовательское событие». Тег передаёт параметры `event_id` и `ticket_placement` из переменных уровня данных. После публикации проверь отправку событий в Tag Assistant и DebugView.

## Мониторинг

Для Cloudflare Workers загрузи `docker/monitor/worker.mjs`, привяжи KV namespace как `MONITOR_STATE`, задай переменную `SITE_URL=https://afisha-rb.by` и секреты `BOT_TOKEN`, `CHAT_ID`. Добавь Cron Trigger `*/5 * * * *`. DNS переносить не нужно. У Worker нет публичного HTTP-обработчика.

Публичные проверки: `/healthz` проверяет ответ приложения и PostgreSQL, `/healthz/import` возвращает 503, если у включённого источника последний сбор неуспешен, отсутствует или был больше 30 часов назад. Ответы не содержат данных источников.

Запускай `python3 docker/monitor/check.py` каждые 5 минут с независимого хоста. Передай `AFISHA_MONITOR_URL=https://afisha-rb.by`, `AFISHA_MONITOR_STATE` (путь к файлу в доступной для записи папке), `AFISHA_MONITOR_BOT_TOKEN` и `AFISHA_MONITOR_CHAT_ID` через защищённые переменные окружения. Не запускай несколько копий одновременно. Оповещение приходит после двух неудачных проверок подряд, повторное — при восстановлении. Для проверки Telegram нужно заранее открыть чат с ботом или добавить его в нужную группу.

Раздел `/admin/operations` доступен администраторам. Он показывает состояние PostgreSQL и импорта при открытии страницы, отчёт внешней проверки и до 100 последних записей каждого журнала. Журналы PHP и Go и последний внешний отчёт хранятся в томе `app_logs`. Журналы ротируются по дню и при достижении 5 МиБ. Хранится до семи архивных файлов на журнал. Архивы PHP старше семи дней удаляются при ротации, а сборщик удаляет просроченные файлы при запуске и затем каждый час.

Раздел `/admin/sql-queries` показывает до 100 последних запросов PHP-приложения через Doctrine. Для каждого запроса сохраняются шаблон с замаскированными литералами, длительность и результат. Записи хранятся в журнале PHP с тем же сроком хранения и отображаются только на странице SQL.

Раздел `/admin/http-requests` показывает до 100 последних обращений к публичному сайту. Caddy записывает время, метод, домен, путь, HTTP-код, IP клиента и User-Agent. Параметры URL, остальные заголовки и запросы к админке, приёму отчётов и Telegram webhook исключены. Файл `access.log` в томе `app_logs` ротируется ежедневно и по размеру. Архивы старше семи дней удаляются при ротации. За обратным прокси поле IP будет точным для посетителя при корректной настройке доверенных прокси в Caddy.

Чтобы отчёты появились в админке, сгенерируй отдельный секрет командой `openssl rand -hex 32` и задай одинаковый `AFISHA_MONITOR_REPORT_TOKEN` в `.env.production` и у одного выбранного внешнего монитора. Для Worker добавь его как Secret. После обновления приложения обнови код монитора и дождись очередной проверки. Через 15 минут без отчёта админка пометит результат устаревшим. Во время полной недоступности сайта оповещения продолжает отправлять внешний монитор, а после восстановления в админке появится время последней неудачной проверки сайта.

### Ресурсы сервера

Чтобы включить Node Exporter, Prometheus и Alertmanager на Linux-сервере, добавь второй Compose-файл к командам релиза. После сборки образов команда поднимет мониторинг и передаст приложению внутренний адрес Prometheus.

```bash
prod() { docker compose --env-file .env.production -f compose.prod.yml -f compose.monitoring.yml "$@"; }
prod up -d --no-build
```

Prometheus опрашивает Node Exporter каждые 30 секунд. В разделе «Мониторинг и журналы» видны загрузка CPU в среднем за пять минут, доступная RAM, свободное место и время замера. По умолчанию карточка показывает раздел `/`. Если данные Docker на другом разделе, узнай его командой `findmnt -no TARGET --target "$(docker info --format '{{.DockerRootDir}}')"` и задай этот путь в `AFISHA_RESOURCE_DISK_MOUNT`. Prometheus проверяет свободное место на всех наблюдаемых разделах с правом записи.

История хранится до 14 дней с лимитом хранения 256 МБ для блоков Prometheus. Интерфейс слушает только loopback сервера на порту `19090`. Для просмотра истории открой SSH-туннель командой `ssh -N -L 19090:127.0.0.1:19090 user@host` и перейди на `http://127.0.0.1:19090`. Для запросов используй `afisha:cpu_busy_percent`, `afisha:memory_available_percent` и `afisha:disk_available_percent`.

Чтобы получать уведомления в Telegram, задай оба значения `AFISHA_RESOURCE_BOT_TOKEN` и `AFISHA_RESOURCE_CHAT_ID` в `.env.production` и пересоздай Alertmanager. При пустых значениях правила видны в Prometheus. Пороги срабатывания приведены ниже.

| Сигнал | Условие |
| --- | --- |
| Диск | Меньше 15% свободного места в течение 10 минут |
| Память | Меньше 10% доступной RAM в течение 10 минут |
| CPU | Загрузка выше 85% в течение 15 минут |
| OOM | Система завершила процесс из-за нехватки памяти |
| Метрики | Нет данных Node Exporter в течение двух минут |

## Обновление и откат

Сохрани резервную копию до миграций и храни её в защищённом месте вне сервера:

```bash
umask 077
prod exec -T postgres sh -c 'pg_dump -Fc -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > afisha-pre-release.dump
```

Проверь копию восстановлением в отдельную базу. Для обновления собери образы с новым тегом, примени миграции и запусти `prod up -d`. Если миграция несовместима со старым приложением, проводи обновление в окно обслуживания. Для отката кода верни предыдущий `RELEASE_TAG` и выполни `prod up -d --no-build`. Если старая версия не совместима с новой схемой, нужен отдельный план восстановления базы; откат образа схему не меняет.

После обновления можно проверить ранее опубликованные карточки на дубли. Команда без `--apply` показывает найденные пары. С `--apply` она помечает карточку как «Дубль», если у основного события совпадают название, место, дата и время начала каждого её действующего сеанса. Расписание обеих карточек сохраняется.

```bash
prod exec -T app php bin/console app:event:mark-duplicates
prod exec -T app php bin/console app:event:mark-duplicates --apply
```

При откате к версии без статуса «Дубль» выполни откат миграции `Version20261120110025` перед запуском старого кода. Он переводит дубли в архив и сохраняет объединённое расписание.
