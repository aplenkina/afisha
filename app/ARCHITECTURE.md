# Архитектура PHP-приложения Afisha RB

Стандарт применяется к новым и изменяемым сценариям Symfony. Существующие
сценарии переводим по одному, сохраняя их публичные контракты и текущее
поведение. Для изменений общей схемы PostgreSQL учитываем и потребителей из
`app-go`. Правила форматирования и удаления неиспользуемого кода действуют
во всём репозитории.

## Модули и зависимости

- Группируем код по предметным модулям. У каждого модуля есть владелец его
  данных и бизнес-правил. Другие модули используют опубликованные прикладные
  контракты или события модуля-владельца.
- `Domain` содержит бизнес-правила и инварианты. Бизнес-решения принимают
  сущности, объекты-значения и доменные сервисы. Домен независим от Symfony,
  Doctrine, HTTP и механизма очередей.
- `Application` содержит сценарии использования. Обработчик получает данные
  через порты, вызывает домен, координирует запись и возвращает результат.
  Порт объявляем во внутреннем слое, которому он нужен. Инфраструктурный
  адаптер реализует порт и подключается через контейнер.
- HTTP, консоль и очередь служат входными адаптерами. Зависимости направлены
  от адаптеров к приложению и домену. Интеграции с БД и внешними системами
  реализуем в исходящих адаптерах.
- Применяем DRY, KISS и SOLID. У бизнес-правила должно быть одно место
  реализации. Делим код по ответственности и передаём зависимости явно.
  Вводим DTO там, где меняется контракт или набор данных, а интерфейс — там,
  где внутреннему слою нужен порт. Выбираем самое простое решение, которое
  сохраняет инварианты и границы модулей.

## HTTP, DTO и ответы

- Symfony Serializer десериализует тело запроса через `#[MapRequestPayload]`,
  а параметры строки запроса — через `#[MapQueryString]`. Используем
  типизированные входные DTO, по возможности `readonly`.
- Для каждого поля явно задаём тип, обязательность и допустимость `null`.
  Для строк задаём допустимую длину, для фиксированных форматов используем
  штатный constraint или паттерн. У коллекций ограничиваем размер и
  валидируем вложенные элементы. Для частичных обновлений различаем
  отсутствующее поле и явный `null`.
- Обычные ограничения задаём `Assert`-атрибутами. Условия между полями одного
  DTO проверяем методом `#[Assert\Callback]` и указываем путь поля для ошибки.
  Переиспользуемую проверку формата выносим в `Constraint` и
  `ConstraintValidator`. Callback работает с данными DTO. Бизнес-инварианты
  проверяет домен при любом способе запуска сценария.
- Контроллер принимает валидированные данные, передаёт команду или запрос
  приложению и передаёт результат HTTP-презентеру. Презентер формирует
  `Response`, включая представление JSON или Twig, статус и заголовки.
  Ошибки API отображаем на HTTP-границе в общий формат со стабильным кодом
  ошибки и путями полей, где это применимо. Авторизацию обеспечиваем на
  соответствующей границе доступа, а бизнес-ограничения действуют при любом
  способе входа в сценарий.

[Маппинг запросов в Symfony](https://symfony.com/doc/current/controller.html#automatic-mapping-of-the-request) · [Callback](https://symfony.com/doc/current/reference/constraints/Callback.html) · [Пользовательские constraints](https://symfony.com/doc/current/validation/custom_constraint.html)

## Symfony Messenger

- Команда запрашивает изменение состояния, запрос читает данные, событие
  описывает произошедшее. Каждый запрос и каждая команда имеют одного
  обработчика. На событие могут подписаться несколько обработчиков.
- Запросы и команды с результатом для текущего HTTP-ответа обрабатываем
  синхронно. Задачу отправляем в очередь, когда допустим отложенный результат.
- Асинхронные сообщения содержат идентификаторы и сериализуемые данные.
  Обработчик выдерживает повторную доставку. Для операций с побочными
  эффектами используем стабильный ключ идемпотентности, общий для всех
  попыток обработки одной логической операции.
- Для очереди задаём ограниченные повторы временных ошибок и транспорт для
  окончательно неуспешных сообщений. Сохраняем совместимость сообщений между
  релизами, включая сообщения, уже находящиеся в очереди. Если публикация
  должна пережить сбой между коммитом и отправкой, сохраняем запись
  transactional outbox в той же транзакции, что и бизнес-изменение.

[Symfony Messenger](https://symfony.com/doc/current/messenger.html)

## PostgreSQL и Doctrine

- Doctrine-репозитории реализуют порты и используют `EntityManagerInterface`
  в инфраструктуре. Граница прикладного сценария определяет, какие записи
  входят в одну транзакцию и когда выполняется `flush()`.
- Уникальность и ссылочную целостность защищаем ограничениями PostgreSQL.
  Прикладной слой переводит ожидаемое нарушение ограничения в ошибку
  сценария. Для конкурентных изменений определяем, как обнаруживаем или
  предотвращаем потерю обновления.
- ORM-маппинг храним в файлах `*.orm.xml` в каталоге
  `src/<Module>/Infrastructure/Doctrine/ORM/Mapping/`. Подключаем каталоги
  через `config/packages/doctrine.yaml`. Doctrine ORM 3 использует XML-драйвер
  для этого внешнего маппинга.
- Схему изменяем через Doctrine Migrations. При поэтапном развёртывании сначала
  добавляем совместимую схему, затем переводим потребителей и данные, после
  чего удаляем устаревшие поля. Проверяем совместимость PHP и Go на каждом
  шаге, если оба используют изменяемую схему.

[Внешний XML-маппинг Doctrine](https://www.doctrine-project.org/projects/doctrine-orm/en/3.7/reference/xml-mapping.html)

## Нагрузка и наблюдаемость

- Для критичных сценариев определяем целевые задержки и допустимую долю
  ошибок. Измеряем p95 и p99, число и время SQL-запросов, а для очередей —
  глубину, возраст старейшего сообщения и окончательные ошибки.
- Ограничиваем размеры выдачи и пакетов. Для списков используем пагинацию
  со стабильным порядком, при необходимости выбираем только нужные поля.
  На репрезентативных данных проверяем N+1 и планы критичных запросов. Кэш
  вводим по результатам измерений и определяем срок жизни и способ обновления.
- Задаём таймауты внешних вызовов. Связываем журналы запроса и фоновой
  обработки через идентификатор корреляции. Исключаем секреты и лишние
  персональные данные из журналов.

[Планы запросов PostgreSQL](https://www.postgresql.org/docs/18/using-explain.html)

## Форматирование и чистота репозитория

- Для каждого языка и формата используем один набор правил для всех модулей
  и команд. Это относится к исходникам, конфигурации, шаблонам, скриптам и
  документации. Для PHP используем PSR-4 и PHP-CS-Fixer с `@Symfony`, для Go —
  `gofmt`. Для остальных форматов используем согласованные настройки редактора
  и форматтеры проекта. Проверки CI используют те же настройки.
- Удаляем неиспользуемые файлы, импорты, переменные, методы, недостижимые
  ветки и закомментированный код. Когда изменение убирает последнего
  потребителя, в том же PR удаляем ставшие лишними регистрации, настройки,
  зависимости и тесты, которые проверяли только удалённое поведение.
- Перед удалением проверяем прямые ссылки, регистрацию в Symfony и Twig,
  вызовы из CLI и Docker, отложенные сообщения и внешних потребителей, где
  применимо. У файлов с ролью в эксплуатации, совместимости, тестах или
  истории миграций есть потребитель даже при отсутствии прямых вызовов из PHP.
  Статанализ и тесты дополняют эту проверку.

[PSR-4](https://www.php-fig.org/psr/psr-4/)

## Тесты и совместимость

- Каждый публичный метод доменного или прикладного сервиса с поведением
  покрываем unit-тестами. Проверяем основной сценарий, значимые границы и
  ошибки. Unit-тесты запускаются без контейнера и БД.
- Для DTO и тонких контроллеров отдельных unit-тестов не требуется. Валидацию,
  авторизацию и формат ответа проверяем функциональными HTTP-тестами.
  Репозитории, ограничения БД и транзакции проверяем интеграционно на
  PostgreSQL. Для асинхронного сценария с побочными эффектами проверяем
  повторную обработку сообщения.
- В CI проверяем форматирование, типы, направление зависимостей и тесты.
  Для изменения публичного контракта проверяем
  совместимость с его потребителями. Для значимого архитектурного решения
  фиксируем причину, затронутые контракты и владельца решения.
